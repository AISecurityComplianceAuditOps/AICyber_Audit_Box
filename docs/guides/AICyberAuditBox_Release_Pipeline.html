The product is an offline ISO 27001 / VAPT / PQC audit appliance: it ships to sites with no internet, so every dependency, model weight and byte of reference data has to be inside the file we hand over. The release studio is a separate tool that turns the repository into that file, refusing to produce one whenever a check fails.

The two halvesHow your source code connects to the tool

The studio is deliberately not part of the product. It never ships to a customer, and keeping it in its own repository makes that structurally true rather than a rule somebody has to remember.

The release studio

AICyber_Audit_Box_Studio  ·  branch main
  • profiles/*.yaml — one per customer: what they bought, their hardware
  • chain.py — the 16 gates, in order
  • licensing.py — Ed25519 signing
  • web.py — the local page an operator uses

The five things the studio reads or runs in your repository

  • git tag / git diff Compares the customer's version with yours to decide patch or full. Only src/ and config/ changed means a patch; anything beneath that layer forces a full bundle.
  • git status Refuses to build from a dirty tree. The decision reads git, but docker build reads the disk — an uncommitted file would ship without ever being considered.
  • pytest Runs the product's own suite inside your repo. A failure stops the release.
  • python -m nuitka Compiles src/ to a single native .so inside python:3.11-slim, then imports it to prove it loads.
  • build_customer_bundle.py Your own bundler, invoked with --version, --out and the runtime limits this customer was sized for.
  • docker inspect / run Opens the built images to confirm the model weights and every runtime asset are actually inside them.

MaterialsTechnology in each layer

The studio carries three dependencies on purpose: every one has to install on a build machine that may itself be offline.

SequenceThe sixteen gates

Ordered deliberately: the cheap checks that can fail run before the ones that take twenty minutes. The chain stops at the first failure and nothing is produced.

01resolve shape Diffs the two versions. Decides patch or full, and names the file that forced a full bundle.
02working tree Refuses uncommitted changes, which would be built but were never compared.
03licence key The verifying key must be in the repo. Without it a customer's install refuses every framework.
04sizing Turns cores and RAM into -np, the shared KV pool, and a concurrent-audit figure.
05tests The product's own suite. 267 must pass.
06compile Nuitka, inside the target image, then imports what it built — compiling is not evidence of working.
07sca Dependency scan. A HIGH finding stops the release.
08bundle Calls your bundler. The result is looked for only where it was told to write it.
09verify The tar must hold the images tar, compose, both installers and the guide.
10verify models Starts the LLM image and lists /models. Three weights, each a plausible size — a 133-byte .gguf is an LFS pointer, not a model.
11app contents Six paths the running app opens: the web UI, knowledge files, report template, licence key, OCR cache, code.
12llm contents The inference binary and the entrypoint that selects which model to serve.
13licence Signs frameworks, expiry and seats for this customer.
14encrypt AES-256-GCM, keyed from that licence. The wrong licence cannot open it.
15checksum sha256 beside the artifact. A truncated transfer usually still opens as a tar.
16publish Artifactory, or left locally and said so.
Why gates 10 and 11 are highlighted. Every other check reads metadata. These two open the built image and look. docker build reports success per instruction, not per file — a COPY whose source moved copies nothing and still exits 0, producing an image that loads and then fails at the customer site.

OperationRunning it

Two front ends over one chain, so the command line and the page cannot drift into checking different things.

# 1. tag the release — patch-vs-full is decided by diffing tags git tag -a v3.25 -m "v3.25" && git push testing v3.25 # 2. the operator page, for whoever does not live in a terminal python -m studio.cli ui --repo "…\audit test_box" # 3. or the command line, same gates, same order python -m studio.cli build profiles/stpi.yaml --version v3.25 --previous v3.24

A customer is a YAML profile: what they were sold, when it expires, how many simultaneous audits, and the machine it runs on. Changing what a site is licensed for is therefore a reviewable commit with an author and a date, not an edit somebody made once.
